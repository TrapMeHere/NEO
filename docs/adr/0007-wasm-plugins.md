# ADR-0007 · Use WASM Component as the plugin ABI

- **Status**: Accepted, 2026-11-15
- **Deciders**: Architecture group
- **Scope**: `neo-plugin` (new), `neo-editor` (command entry), `neo-ui` (panel registration), `neo-api` (token isolation)
- **Related**: [15 Plugin System](../15-plugin-system.md) · [02 Workspace and Dependency Rules](../02-workspace-and-dependency-rules.md) · [06 Editing Core and Undo](../06-editing-core-and-undo.md)

## Background

To replace the JOSM workflow, NEO must allow third-party extensions: JOSM's plugin ecosystem (validators, imagery sources, importers, drawing tools) is one of the real reasons it has survived so long. If NEO does not provide a plugin mechanism, the goal of "fully replacing JOSM" does not hold.

The question is **what to use as the ABI**. There are three candidates:

1. **Rust dynamic libraries** (`cdylib` + hand-written `extern "C"`);
2. **`abi_stable 0.11.3`**'s `StableAbi` dynamic libraries;
3. **WASM** (core module or Component Model).

Rust still has no stable ABI. `abi_stable` solves "struct layout stability" but not three things: (a) plugins must be compiled by the **same rustc version**, otherwise `std`'s `TypeId`/trait object layout may be incompatible; (b) when the plugin and host each statically link the same crate, global singletons (`tracing` subscriber, `wgpu::Instance`, `rayon` thread pool) get **one copy each**, producing hard-to-diagnose failures like "logs lost" and "GPU device conflicts"; (c) plugin code runs in the same process and with the same privileges as the host, so a single `unsafe` or infinite loop can take down the editor. For a desktop app that handles users' unuploaded edits and holds OAuth tokens, none of these three is acceptable.

The cost of WASM is clear: a cross-boundary contract (WIT), explicit capability-by-capability exposure by the host, and serialization costs for cross-boundary calls. But these costs are **one-time, testable, versionable**; the cost of ABI drift is continuous and unpredictable.

## Decision

The only ABI for plugins is the **WASM Component Model**, with `wasmtime 50.0` as the runtime, and the contract defined by the WIT world `neo:plugin@1.0.0` generated by `wit-bindgen 0.63`. Specific clauses:

1. **Contract versioning**: `package neo:plugin@x.y.z` uses semantic versioning; adding optional exports is a minor change, changing types or removing functions is a major change. The host can link multiple major versions at once.
2. **Capability allowlist**: the plugin's `manifest.toml` declares required capabilities (`command`/`ui`/`events`/`network`/`filesystem`/`imagery`), and the runtime allows "declared ∩ user-authorized"; `read` (read-only snapshot queries) is the only implicit capability.
3. **Single write path**: plugins cannot touch `neo-store`; they can only `submit-command` to the queue, which the `neo-editor` commit pipeline executes—so every plugin modification is verifiable, journalable, and undoable.
4. **Declarative UI**: plugins return a draw list, which the host renders with egui; `egui::Context` is not exposed, preventing arbitrary drawing and frame blocking.
5. **Hard resource limits**: `consume_fuel` + `epoch_interruption` + memory cap (64 MiB by default) + serial dispatch per instance; exceeding a limit traps and disables that plugin without affecting others.
6. **The C ABI bridge is an exception channel**: the very few plugins that must access native libraries (e.g., proprietary format SDKs) may go through an independent C ABI subprocess bridge, requiring a separate ADR, and it is **not** the default path.
7. **Signing**: official distribution requires a detached signature over `manifest.toml` + `component.wasm` inside `.neopkg`; unsigned packages can only be loaded in developer mode.

## Alternatives

| Option | Why rejected |
|---|---|
| `cdylib` + hand-written `extern "C"` | Every type needs manually agreed `Vec`/`String` lifetimes; UB risk at every boundary; no sandbox |
| `abi_stable 0.11.3` | Solves only layout, not rustc version coupling or dependency-singleton conflicts; still no sandbox; one binary per platform per architecture |
| Subprocess + custom IPC | Best isolation, but every query needs a serialized round trip, and the latency is unacceptable for interactive panels (refresh on selection change); kept as an optional mode for high-risk plugins |
| Embedded JS engine (JSR-223/GraalJS equivalent) | Introduces a second sandbox surface and significant size; script-style needs are covered first by `neo-validate` declarative rules |
| No plugins | Gives up the "replace the JOSM workflow" goal outright |

## Consequences

**Positive**

- Plugin binaries work across platforms and across NEO minor versions; distribution is a single-file zip.
- Supply chain and permissions are auditable: the permission list is shown at install time and re-validated at runtime.
- Plugin crashes, infinite loops, and memory overruns are isolated within their own instance; host data cannot be directly corrupted.
- Forcing everything through the command pipeline means plugin-generated edits automatically get undo/journal/conflict detection.

**Negative / costs**

- Must maintain the WIT contract and backward-compatibility tests (golden plugins + CI matrix).
- The data shapes of cross-boundary calls are limited (no reference passing, no zero copy), so batch queries must be designed as "fetch many at once".
- Plugin authors need Rust (or any WASM source language) + the component model toolchain, a steeper learning curve than writing Java plugins.
- The host must implement `HostApi` (read snapshot/submit command/HTTP/files) in `apps/neo-desktop`; that implementation inherently crosses layers and is a new coupling point.

**Prerequisites that must be completed**

- The legal dependency set of `neo-plugin` (`neo-core`, `neo-editor`) has **no** read-only spatial query capability (queries and indexes live in `neo-store`). Option A in [15 §2.7](../15-plugin-system.md) must move the `MapQuery` trait down into `neo-core` (or add a new leaf crate `neo-query`), and register it in the [02](../02-workspace-and-dependency-rules.md) whitelist. **Until this is done, plugins can only see the selection set, and `query-bbox` cannot be implemented.**
- The signature verification library is not in the dependency list; its selection (Ed25519) must be tracked separately.

## Verification

| Verification item | Method | Pass criterion |
|---|---|---|
| Contract compatibility | Keep a v1 golden plugin and load it with the new host in CI | Loads successfully and behavior unchanged |
| Permission isolation | A plugin without `command` declared submits a command | Returns `permission-denied`, `neo-editor` has no transaction |
| Resource isolation | Infinite-loop / out-of-memory / timed-out plugin | After trap, the host frame loop is normal and other plugins in the same process keep working |
| Data safety | Plugin attempts to modify the store directly | Impossible at compile time (no such import), and no interface at runtime |
| Version gate | A plugin with `api = "2.0"` | Refused to load + readable error |
| Distributability | Install `.neopkg` on a machine without a Rust toolchain | Loads and runs successfully |
| Performance | Event dispatch and panel rendering overhead | [to be measured, see docs/14-performance-and-verification.md] |
